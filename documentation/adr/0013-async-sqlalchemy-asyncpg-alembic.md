# ADR-0013: Async SQLAlchemy + asyncpg + Alembic

## Context

The backend is an async-first FastAPI service over PostgreSQL. It needs a data-access
layer and a migration tool that support a fully async request path with no synchronous
driver blocking the event loop, typed models that carry the project's invariants — UUIDv7
primary keys (ADR-0006), user-scoped ownership (ADR-0004), native enums (ADR-0008) — and
versioned schema evolution that is reviewable and reversible.

## Decision

- **ORM:** SQLAlchemy's modern typed declarative API (`Mapped[...]` / `mapped_column`),
  with an async engine and an async session factory.
- **Driver:** `asyncpg`, an async PostgreSQL driver.
- **Migrations:** Alembic, configured to run async migrations inside a synchronous
  migration context. Autogenerate is a starting point, but every migration is reviewed by
  hand, since autogenerate misses enum changes and server defaults.
- **Session lifecycle:** one session per request, provided by a dependency that opens,
  yields, rolls back on any exception, and closes — never a module-global session.
- **Base and mixins:** a declarative base plus reusable mixins — a UUIDv7 primary-key
  mixin (an application-side default plus a PostgreSQL-native server default), a
  timestamp mixin, and an owned-by-user mixin for user-scoped rows. New models compose
  these mixins rather than re-declaring columns.
- **Enums:** native PostgreSQL enum types, not string columns (ADR-0008).

## Consequences

- The async path stays non-blocking end to end. The same session machinery is reused
  unchanged by the platform's background worker (ADR-0011), which runs scheduled
  reconcilers rather than request work moved off the hot path. Two properties of that
  reuse are load-bearing: the worker's reclamation passes single-flight on a PostgreSQL
  advisory lock taken through this same engine, rather than a Redis lock, chosen because
  Redis is the store that reconciliation work exists to distrust; and every worker process
  builds its own settings from the environment alone, since the multiprocessing start
  method used in production inherits nothing from a parent process.
- Typed models are checked by the project's type-check gates, so a mis-typed column or a
  missing scope surfaces as a type error, not a runtime surprise.
- Alembic gives reviewable, reversible schema history for the control-plane database. A
  generated app's own database (ADR-0028) is a separate lineage entirely: its schema and
  migrations are authored and owned by the app itself, not by this control-plane tooling.
  The platform's responsibility stops at creating and tearing down that database; what is
  inside it is the app's own concern.
- Async migrations and hand-reviewed autogenerated diffs add a little friction, accepted
  for correctness — enum and default drift is the classic autogenerate miss.
